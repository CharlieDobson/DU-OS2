XArchive for OS/2 - port notes
==============================

THE BACKEND IS A VERBATIM COPY, AND IS MEANT TO STAY ONE
    Every source in this directory except PMMAIN.C, OS2PLAT.C, COMPAT.C and
    windows.h is a byte-for-byte copy of the file of the same name in
    S:\CPP\DU32\XARCHIVE.  They are copies rather than shared files because
    the two trees build with different toolchains and layouts; nothing but
    discipline keeps them identical.

    To check, from anywhere:

        for %F in (ARCFILE.C SZARC.C ZIPARC.C RARARC.C RAR3DEC.C RAR5ARC.C ^
                   DISKARC.C LZMADEC.C CRC32.C ARCPREF.C ^
                   ARCDEFS.H ARCFILE.H ARCPREF.H SZARC.H ZIPARC.H RARARC.H ^
                   RAR3DEC.H RAR5ARC.H DISKARC.H LZMADEC.H CRC32.H ^
                   PLATFORM.H) do ^
          fc /b %F S:\CPP\DU32\XARCHIVE\%F

    Any difference is drift, not a port: the platform is dealt with by
    #if defined(__OS2__) inside those files and by the windows.h shim, never
    by editing a copy.  If one of them has to change for OS/2, change it in
    the DU32 tree behind an __OS2__ guard and copy the whole file back.

    Last synced 2026-09-06, six files: LZMADEC.C for the SpecPos index below,
    and ARCFILE.C, ARCPREF.C, ARCDEFS.H, ARCFILE.H, ARCPREF.H for the
    removal of the MemoryLimitMB preference.  Before that, 2026-09-01.

      MemoryLimitMB  gone from XARCHIVE.INI, along with ArcMemSetLimit and
        ArcMemReport's 'forced' out-parameter (the PM front end never called
        ArcMemReport, so nothing here had to change for the new signature).
        The budget is measured from the machine and a hand-set cap could only
        make that worse in either direction.  ARCPREF.C still NAMES the key in
        IsKnownKey, marked retired: keys it does not recognise are preserved
        across a save, so a key merely dropped from the reader would live in
        the file forever.  MKOS2.CMD builds clean and MKTEST.CMD passes.

      LZMADEC.C  the SpecPos index in the distance decode was a chain of
        pointer + and - with UNSIGNED operands (dist, posSlot) in the address
        arithmetic at every step; MSVC 2.2 warns about it on the Win32s build.
        It is one plain int now, added to the pointer once.  No behaviour
        change (modern MSVC /Wall and wcc386 -bt=nt -w4 -za are silent either
        way, and every CLI output is byte-identical), but it is in the shared
        decoder, so it belongs here too.  Note for the next line number that
        gets quoted: MSVC 2.2 reports a multi-line statement at its CLOSING
        line, which sent the first two attempts at this to the wrong line
        entirely.

    The 2026-09-01 sync carried eight files - ARCFILE.C,
    SZARC.C, ZIPARC.C, RARARC.C, RAR5ARC.C, DISKARC.C, LZMADEC.C and
    ARCDEFS.H - for three fixes, all of them from DOS field reports and all of
    them equally true here:

      LZMADEC.C WinFlush  handed the sink its output only when the ring
        WRAPPED, so the first delivery was one whole dictionary's worth: no
        progress callback and no bytes in any file until that much had been
        decoded.  Measured under DOS/32A: 0 s at a 1 MB dictionary, 45 s at
        16 MB.  It now also flushes every 64K.  The bytes stay in the ring for
        matches, so this is a delivery-size change and not a correctness one.

      ArcFsName / ArcNameVerdict  a name can now produce NOTHING, and the
        backends have to be told.  Two ways: an entry that is just "." (the
        destination said the long way - it used to become a stray directory
        called "_"), and the user answering Skip or Cancel at the 8.3 prompt.
        Cancel used to mean "keep the automatic name", so cancelling extracted
        the whole archive anyway.  Every backend now reads ArcNameVerdict()
        after building an output path.

      ArcFsName( ..., int isDir )  a folder that has to be SHORTENED to 8.3
        now keeps no extension: "3D FloorPlan Designer 2.0 for DOS (1993)
        (3.5-720k)(5.25-360k)" was becoming 3DFLOO~1.25- - three characters of
        a floppy size presented as a file type - and is now 3DFLOO~1.  A folder
        that already fits (DATA.OLD) is untouched, and files keep their
        extensions.  The caller has to say which it is, because 7z records
        directories in an attribute with no trailing separator and the name
        cannot be read for it.  Ten call sites; the signature was changed
        rather than overloaded so the compiler would find them all - which it
        did, here as well as in DU32.

      The 8.3 prompt contract  gained ARC_SN_SKIP and ARC_SN_ABORT.  No PM
        code installs a prompt (only the DOS TUI does - 8.3 mangling is a DOS
        and Win32s-on-FAT problem), so nothing in this tree calls it; the
        backend still has to honour it, which is what the unit test checks.

    BUILD\OS2T.C gained an ArcNameVerdict stub and three cases around
    WriteDirEntry - OK creates the directory, SKIP and ABORT do not.  It found
    the change on its own: the first build after the sync failed to LINK on an
    undefined ArcNameVerdict, which is exactly the alarm this test exists to
    raise.  Verified discriminating: with the verdict check removed from
    WriteDirEntry it fails the SKIP and ABORT cases and passes the rest.

    The 2026-08-29 sync carried ZIPARC.C alone:

      ZIPARC.C FindEndRec  found the zip end-of-central-directory record by
        walking backwards from EOF one byte at a time, an fseek and a
        four-byte fread per position.  On a file that is not a zip the loop
        runs to exhaustion - 65515 seek/read pairs - and every .exe is offered
        to this parser for the sake of self-extracting archives.  Under
        DOS/32A that was 4.2 seconds spent deciding a file was not an archive.
        The record can start no earlier than 65557 bytes from EOF, so the tail
        is now read once and scanned in memory, which is what SZARC.C's
        SzFindStartHeader already did for the 7z signature.

        Nothing about this is DOS-specific: a per-byte seek is slower than one
        read on OS/2 too, though a 32-bit OS with a real file cache will hide
        far more of it than a DOS extender did.  The value here is that the
        two trees do not drift, and that the OS/2 build stops making the same
        pass over every .exe the user points at.

    The 2026-08-28 sync carried two bug fixes across:

      SZARC.C BuildPath  joined the destination and the entry name with
        wsprintf( "%s\\%s" ), so a destination that already ended in a
        separator got a second one.  The root of a drive is spelt "C:\", so
        extracting there produced "C:\\FILE.TXT" - which is not a file on C:
        at all.  OS/2, like DOS, reads a drive letter followed by two path
        characters as a UNC network name.  Every backend now joins with
        exactly one separator and counts '/' as one too.

      SZARC.C SzDictCost  the six LZMA dictionary checks weighed the size the
        coder DECLARES against the memory budget.  A dictionary is a window
        on to output already produced, so LZMADEC's WinOpen has always
        allocated min(dictSize, unpackSize) - and the buffered entry points
        allocate no dictionary at all.  A 64 MB declaration over a folder
        unpacking to 8 MB cost 8 and was refused for wanting 64.  The checks
        now weigh what gets allocated.

    ARCFILE.C's probe-bound change in the same sync is DOS-only by
    construction: OS/2 keeps the DosQuerySysInfo figure as a hard cap on the
    malloc probe, because a large allocation here succeeds by growing the
    swap file and would otherwise measure address space rather than RAM.

BUILD\MKTEST.CMD - the backend unit test
    The OS/2 executable cannot be run on the Windows box this is cross-built
    on, and the BuildPath bug above is invisible to both emulators that are
    available: DOSBox forgives a doubled separator and so does Windows NT.
    So MKTEST.CMD compiles THIS TREE'S SZARC.C, through THIS TREE'S
    windows.h, as an ordinary NT console program and checks the string
    BuildPath builds rather than the file that appears afterwards.

    It is a unit test of the two fixes above, not a substitute for running
    XARCHIVE.EXE on OS/2.  Verified discriminating: with BuildPath reverted
    to the old wsprintf it fails exactly the four separator cases and passes
    the rest.

WHAT THIS PORT DOES NOT HAVE (and neither does the Win32s GUI)
    The DOS TUI gained several things in the 2026-08-28 round that live
    entirely in its front end.  Most do not apply here - PM ticks a menu item
    natively (IDM_ARCHIVE_PATHS already does), Alt already reaches the menu
    bar, and there is no folder-view/flat-view mode on this front end at all.

    Two DO apply, and are absent from BOTH GUIs, so the two are still in sync
    with each other:

      - a memory diagnostic.  ArcMemReport() is in the shared backend and
        reports what the system claimed, what the largest block actually
        obtained was, and the budget.  An OS/2 user who hits "not enough
        memory" has the same unanswerable question a DOS user did.  The
        wording would differ: the XMS 2.0 64 MB ceiling that explains it on
        DOS has no counterpart here, where the cause is DosQuerySysInfo or
        genuine fragmentation.
      - the short-name prompt.  ArcSetShortNamePrompt() is in the shared
        backend and Os2NamesNeed83() already returns 1 for a FAT target, so
        an OS/2 user extracting to a FAT volume gets the same LONGFI~1.TXT
        renaming with no say in it.  Adding it needs a new dialog resource.

    Both were left out deliberately: adding menu items to two GUIs that
    cannot be run from here is a scope-and-risk call, not a mechanical sync.

    Also unsynced and deliberate for now: the About box says "XArchive v1.0"
    in both GUIs while the DOS TUI says v1.2.

THE PM FRONT END ASKS FOR THE PASSWORD UP FRONT, AND THE OTHER TWO DO NOT

    This is the one place the OS/2 port genuinely has to differ, so it is
    worth writing down rather than rediscovering.

    The DOS and Win32s front ends retry in a LOOP around the failed call:

        do { rc = ArcSomething( ... ); } while ( PasswordRetry( rc ) );

    That is impossible here.  Archive work runs on a worker thread which may
    make NO PM calls, so the prompt can only happen on the UI thread once the
    job has already finished - and by then the worker has freed the selection
    array that running the job again would need.  Rather than complicate who
    owns that array, PMMAIN asks BEFORE starting any job that will touch entry
    data (EnsurePassword, called from RunExtraction and DoTest).

    That is the better order anyway: being asked at the START of a long
    extraction beats being asked at the end of a failed one.

    A wrong password is then reported by ArcOnDone, which also CLEARS the
    stored one, so the next attempt asks again instead of failing identically
    and silently.

    The exception is an encrypted HEADER (7-Zip -mhe=on), which cannot be
    listed at all without the password.  There ArcOnDone does restart the job,
    because an open job allocates nothing - g_job.openPw carries the password
    into the worker, and ArcOpenPw does the work.  On success that password is
    carried into g_password, so the user is not asked a second time for the
    entry data.

    New resources: IDD_PASSWORD, IDC_PW_EDIT, IDC_PW_PROMPT.  The entry field
    uses ES_UNREADABLE, which is PM's answer to Windows ES_PASSWORD.  The
    prompt is a CONTROL rather than fixed text because it has two jobs - asking
    the first time, and saying the last attempt was wrong; a second identical
    dialog reads as though the program ignored what was typed.

    NOT RUNTIME-VERIFIED.  This builds and the backend unit test passes, but
    the PM dialog itself has not been seen on a real OS/2 machine - same
    standing caveat as the rest of this port.  The backend half of it IS
    verified, on DOS and against 7-Zip-written archives, and that is the half
    the cryptography lives in.

RE-SYNC 2026-09-12 (RAR3 ENCRYPTION)

    RARARC.C/.H, ARCCRYP.C/.H and ARCFILE.C were re-copied from DU32 after
    RAR3 (RAR 2.9/3.x/4.x) AES-128-CBC decryption was added.  The whole backend
    was then re-checked file by file and is byte-identical to DU32's again.

    Nothing in the PM front end changed: the password dialog added last round
    already routes through ArcSetPassword / ArcNeedsPassword, and both now
    answer for RAR4 the same way they already did for RAR5 and zip.  The one

    encrypted RAR4 opened with a password no longer needs a second call.

    BUILD\MKOS2.CMD and BUILD\MKTEST.CMD needed no edits: ARCCRYP/AES/SHA
    joined both lists last round and RARARC was always in them.  The PM build
    was re-run and links clean.

    as the rest of this port.  The backend half IS verified, on DOS and against
    WinRAR 5.0-written archives.

BACKEND RE-SYNC 2026-09-13 - encrypted headers (-hp)
===========================================================================

Five files copied forward from S:\CPP\DU32\XARCHIVE, no new files, and all 28
shared files verified byte-identical afterwards (0 mismatches; only COMPAT.C,
OS2PLAT.C and PMMAIN.C are OS/2-only, as always):

    RARARC.C/H    RarOpenPw and RarReadBlock - RAR4 -hp
    RAR5ARC.C/H   Rar5OpenPw and Rar5ReadBlock - RAR5 -hp
    ARCFILE.C     both RARs now take the password at OPEN time, like 7z

The PM front end needed no change, and that is worth noting rather than just
being lucky: it already prompted and retried through ArcOpenPw whenever an
open returned SZ_ERR_PASSWORD, because 7z's encoded header needed exactly
that.  Two more formats with locked directories arrived behind a contract
already in place.

Both openers also refuse to report an EMPTY archive when no encrypted header
could be read, and they tell the two causes apart: a short read is truncation
(SZ_ERR_READ), a full read whose CRC fails is the password (SZ_ERR_BADPASS).
Calling a truncated archive a wrong password would send the user off retyping
a right one - last round's PPMd misreport wearing a different hat.

MKOS2.CMD links clean and MKTEST.CMD passes (ALL PASS, 0 failures).

BACKEND RE-SYNC 2026-09-13 (multi-volume)

    The DU32 backend gained multi-volume support and VOLIO.C/VOLIO.H are new
    files in it, so both were copied across and both build scripts updated:
    MKOS2.CMD (the PM app) and MKTEST.CMD (the backend unit test, which
    #includes SZARC.C and therefore needs every symbol SZARC.C now references).

    Verified after the sync: 30 shared files compare byte-identical against
    S:\CPP\DU32\XARCHIVE, MKOS2.CMD links clean, and MKTEST.CMD reports
    ALL PASS (0 failures).

    Nothing in the volume layer is platform-specific - it is stdio plus
    filename arithmetic - so there was no OS/2-side work beyond the sync.  The
    one-open-handle discipline it uses was chosen for DOS, where handles are
    scarce; OS/2 would not have needed it but is not harmed by it.

BACKEND RE-SYNC 2026-09-13 (solid chains)

    RAR3DEC.C, RAR3DEC.H and RARARC.C re-copied from S:\CPP\DU32\XARCHIVE
    after the solid-chain fix.  30 shared files, 0 mismatches (fc /b).

    The fix: RAR closes each member of a solid chain with a block trailer
    saying whether the next member brings fresh Huffman tables, and nothing
    read it, so members after the first decoded with stale tables whenever
    the encoder had started new ones.  A correct archive was reported corrupt
    - or, on an encrypted chain, reported as a wrong password when the
    password was right.  RAR2 is deliberately untouched: unpack v20 has no
    such trailer, announcing new tables inline with symbol 269.

    BUILD\MKTEST.CMD still passes.  It does not link RAR3DEC.C, so it does
    not cover this change; the evidence is the twelve-fixture solid suite on
    the DU32 side plus the real-DOS byte comparison.  MKOS2.CMD links clean.

BACKEND RE-SYNC 2026-09-13 (group separators)

    NUMFMT.C and NUMFMT.H are NEW and shared; PMMAIN.C now formats the Size
    and Packed columns and the Archive Info totals through them, and calls
    NumFmtInitFromEnv() before WinInitialize so the first listing drawn is
    already right.  BUILD\MKOS2.CMD gained NUMFMT in both the compile loop
    and the link list.  32 shared files, 0 mismatches.

    OS/2 gets its separator from DosQueryCtryInfo's szThousandsSeparator -
    the same field the OS/2 toolkit header in DOS6SRC\45\tl\inc\bsedos.h
    declares.  The per-record szSize/szPacked buffers grew from 16 to
    NUM_FMT_U32_MAX (24) because a grouped UInt32 with a multi-byte separator
    would not fit 16.

    MKOS2 links clean; MKTEST still ALL PASS (it does not link NUMFMT).

COMMENT DIALOG 2026-09-13

    The Archive pulldown gained "~Comments...", and RES\XARCHIVE.RC gained
    IDD_COMMENT - a read-only WC_MLE with BOTH scrollbars, filled the same way
    the Info box fills its own (MLM_SETIMPORTEXPORT then MLM_IMPORT with
    refresh disabled across the pair, so a long comment does not repaint once
    per line) and given "10.System Monospaced", because comments are routinely
    laid out in columns or as ASCII art and PM's default font is proportional.

    IDD_COMMENT is 111 and IDM_ARCHIVE_COMMENT is 210 - the same numbers as
    the Win32s tree, per the rule at the top of RES\RESOURCE.H.  The CONTROL
    id is 1020 in BOTH trees: this one's next free was 1019 and the Win32s
    tree's was 1017, so 1020 is the first free on both sides and each header
    notes the skipped numbers.

    The text comes from the new shared ArcCommentText(), which rewrites every
    line ending as CRLF - the MLE runs a lone LF straight on and would show a
    twenty-line comment as one very long line.

    Verified: MKOS2 compiles, links and binds, and the built XARCHIVE.EXE
    contains "Archive Comment" and "Comments...", so the resources are really
    in it.  MKTEST still ALL PASS.  32 shared files, 0 mismatches.

    KNOWN, AND NOT FROM THIS CHANGE: a RAR4 comment written by WinRAR 5 does
    not reach the dialog - RARARC.C reads only the old 0x75 block and only
    when stored, while WinRAR 5 writes a PACKED NEWSUB (0x7A).  The menu item
    greys as though there were none.  ZIP comments work.

      - A startup warning when the machine cannot manage even the cheapest
        extraction, shown once with Say() after WinShowWindow so it has a
        parent to be modal over.  A WARNING and not a refusal: listing costs a
        few KB an entry and works fine below that line, and being able to see

        cannot quote different numbers at the user; this port appends its own
        closing sentence.

        when it is the bad news.  On a machine with room, "and 1,757,217 KB
        free" is a number nobody needs.

        1024 bytes and the addition is well inside it.

    ArcExtractItems and ArcTestAll, so this port cannot forget it and gets the
    same refusal as the other two for free.  It is per ARCHIVE, not per
    format: a zip costs 173 KB whatever it holds, while two .7z files that
    list identically can want 64 KB and 64 MB.

    ALSO FROM THE BACKEND, with no PM-side work: RAR4 comments written by
    WinRAR 5 now reach the comment dialog added in the previous block.  That
